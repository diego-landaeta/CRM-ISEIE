## 3. Decisiones tecnicas clave de la sesion

### Comisiones (CRM-180 rediseño)
- Modelo nuevo: **regla por (project_id, user_id, pct)** con `producto_id` OPCIONAL como override
- `base_calc` ENUM: `cobrado` o `vendido` (sobre que se calcula)
- `condicion` JSONB para reglas tipo "solo si importe > 500"
- UI sin SQL: operadores +, campos, combos AND/OR
- **Aisladas estrictas por proyecto**: en ISEIH no veo comisiones de Psiko
- Ventas brutas / netas / cobradas / por cobrar como KPIs del gestor

### Webhook vs UTM (clarificacion)
No son alternativas. Webhook = transporte, UTMs = datos dentro del body. Siempre juntos.

### Forms (CRM-175)
- NO builder drag-drop. Solo **plantillas pre-hechas** (Contacto basico, Lead con producto) con toggles opcionales
- **Shadow DOM** para aislar CSS del landing
- Hereda del proyecto activo: logo, producto_label, productos, color primario
- 3 embeds: script tag, iframe, webhook JSON con ejemplos Make/Zapier/curl/Brevo

### Modulos por proyecto (CRM-178)
- Cada proyecto activa/desactiva modulos individualmente
- Middleware server-side rechaza endpoints de modulos deshabilitados
- Ejemplo: Tarot IA solo `platform_users` + `accounting_income`
- Reemplaza CRM-172 (modo IA binario)

### Multi-instancia (CRM-197)
- 2 capas: INSTALL TIME (`.env` `ENABLED_MODULES`) + RUNTIME (por proyecto)
- Un proyecto no puede activar modulo que el server no tenga
- Mismo codigo base, deploys diferenciados

### WooCommerce (CRM-177)
- Importador flexible: cada tienda tiene sus meta_data con nombres custom
- Admin mapea visualmente: `meta_data.estudiar → products.descripcion`
- Bulk mapping: auto-detectar, copiar-a-todos, copiar-de-otro-proyecto
- Update via wc_product_id (no duplicar), variaciones en JSONB
- Categorias nuevas se crean automaticamente respetando limite 5 niveles (CRM-195)

### Storage (pattern aplicado hoy)
- R2 sin configurar (no hay credenciales todavia)
- Uso `backend/src/shared/services/localStorage.service.js` para todo upload
- Dir: `/var/crm-uploads/` (persiste entre deploys)
- Migrar a R2 despues: solo cambiar import, interfaz identica

### Pagos con fecha (CRM-184)
- TODOS los pagos llevan fecha NOT NULL (conversion_payments, accounts_payable_payments, commissions.fecha_pago, expenses.fecha)
- Frontend: input fecha siempre visible, default hoy, backdate permitido
- Excepcion: cuotas previstas tienen `fecha_vencimiento` (futura) vs `fecha_cobro` (al pagar)

## 5. Como replicar este setup en otro server

1. Clonar repo `github.com/esos2dev-oss/CRM`
2. Instalar PostgreSQL 17, Node v24, PM2, Nginx
3. `createdb crm_test_db`
4. Correr migraciones `backend/migrations/001..013_*.sql` en orden
5. `GRANT ALL` al user `crm_user`
6. Ejecutar `backend/seeds/reset_beta.sql` para 2 proyectos + usuarios base
7. `.env` con JWT_SECRET, REFRESH_SECRET, ENCRYPTION_KEY, DATABASE_URL
8. `mkdir -p /var/crm-uploads/logos && chown claude:claude /var/crm-uploads`
9. `pm2 start ecosystem.config.js --only crm-api-staging`
10. Nginx reverse proxy al puerto 3002 (template en `nginx/`)
